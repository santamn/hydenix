# 10. CI の仕組み

このリポジトリで GitHub Actions が何をしているかをまとめます。

## 全体像

CI の定義は `.github/workflows/` 以下にある 8 個のワークフローファイルと、依存更新を担当する `.github/dependabot.yml`・`.github/renovate.json` に分かれています。実行基盤は GitHub Actions で、`nix flake check` のような Nix 由来のチェックも含めてすべてこの上で動きます。検証系のワークフローは florianvazelle/hydenix から引き継いだものがほぼそのまま残っていますが、依存更新まわりはこのフォークで組み替えました。`update-flake-lock.yml` を廃止して `flake.lock` の更新を renovate に一本化し、一度も rev を進めていなかった `update-themes.yml` を `update-branch-pins.yml` に作り直しています。`flake.nix` の `checks` に検証対象を増やしたのもこのフォークです（[08-improvements.md](./08-improvements.md) の A-0）。

上流はアーカイブされたので、これらのワークフローが動いているのはもうこのリポジトリだけです。`renovate.yml` / `update-branch-pins.yml` が作る自動更新 PR も、`pages.yml` が公開する GitHub Pages も、すべてこのリポジトリ自身に対して作られます。`flake.lock` の週次更新とブランチピンの更新は自動でマージされますが、HyDE や Hyprland のバージョンを上げる PR と Dependabot の PR は人がマージするまで残ります。放置すると誰も拾いません。

これらの仕組みの大半（treefmt・typos・zizmor・renovate・mdbook での Pages 公開）はもともとの本家である richen604/hydenix にはなく、florianvazelle 氏がフォークした際に追加したものです。経緯の要約は [README.md](./README.md) の本家からの主な変更点を参照してください。ここではその中身を実際のワークフロー定義に沿って詳しく見ていきます。

ワークフローの `on:` はほとんどが `workflow_dispatch` と `push`（`main` ブランチと tag のみ）と `pull_request` の組み合わせです。`push` の対象が `main` に限られているため、`ja` ブランチへの push はこの条件に一致せず CI は起動しません。docs-ja/ を読みながら CI の挙動が気になったときは、常に `main` 相当の内容に対して実行されていると考えてください。

## ワークフロー一覧

| ファイル | 主なトリガー | 役割 |
|---|---|---|
| `commit-lint.yml` | pull_request | PR に含まれるコミットメッセージが Conventional Commits に従っているか検査する |
| `flake-check.yml` | workflow_dispatch, push（main・tag）, pull_request | ルートと `template/` の flake を評価し、`checks` に登録されたパッケージをビルドする |
| `flint.yml` | workflow_dispatch, push（main・tag）, pull_request | `flake.lock` の中で同じ依存が複数バージョン混在していないか検査する |
| `typos.yml` | workflow_dispatch, push（main・tag）, pull_request | リポジトリ全体のスペルミスを検査する |
| `zizmor.yml` | workflow_dispatch, push（main・tag）, pull_request | ワークフロー定義自体をセキュリティ観点で静的解析する |
| `renovate.yml` | workflow_dispatch, schedule（毎週日曜 0 時 UTC）, pull_request | renovate 設定を検証し、依存更新 PR（`flake.lock` の更新を含む）を作成する |
| `update-branch-pins.yml` | workflow_dispatch, schedule（毎日 0 時 UTC） | テーマと HyDE master の commit 固定を、追っているブランチの先頭へ進める PR を作ってマージする |
| `pages.yml` | workflow_dispatch, push（main）, pull_request | `docs/` を mdbook でビルドし、`main` への push 時のみ GitHub Pages に公開する |
| `dependabot.yml` | GitHub 側の機構、毎日 | `.github/workflows/` が参照する Action のバージョンを更新する PR を作成する |

以降はこれを 3 つに分けて説明します。PR を検証するもの、スケジュール実行で自動更新 PR を作るもの、ドキュメントを公開するものです。

## PR を検証するワークフロー

`pull_request` イベントで起動する次の 5 つのワークフローが PR を検証します。ブランチ保護ではどれも必須にしていないので（理由は後述の GITHUB_TOKEN で作る PR の制約を参照）、結果を見てからマージするのは人の役目です。

### commit-lint.yml — コミットメッセージの検査

PR のときだけ起動します。`fetch-depth: 0` で全履歴を取得したうえで `.commitlintrc.json` を `$HOME/.commitlintrc.json` にコピーし、`commitlint --from <base sha> --to <head sha>` で PR に含まれるコミットだけを検査します。ルールは type が build・chore・ci・docs・feat・fix・perf・refactor・revert・style・test のいずれかであること、先頭行が 72 文字以内であること、末尾にピリオドを置かないこと、type と scope が小文字であることです。書き方の例は [09-fork-workflow.md](./09-fork-workflow.md) にまとまっています。

### flake-check.yml — flake の評価とビルド

ルートの `nix flake check` を実行したあと、`template/` 側でも同じことをします。`template/flake.nix` はふだん `inputs.hydenix.url = "github:santamn/hydenix"` を参照していますが、これをそのまま評価すると変更中のコードではなく `main` の最新を見てしまうので、CI では `sed` で一時的に `path:../` に書き換えてから `nix flake check` を実行し、終わったら `flake.nix` を `git checkout` で戻して `flake.lock` を削除します。`sed` のパターンはこの URL と一字一句一致していないと黙って空振りするので、`template/flake.nix` の入力先を変えるときは `flake-check.yml` の `sed` も一緒に直す必要があります（以前は `update-flake-lock.yml` にも同じ `sed` がありました）。こうすることで、テンプレートが今のブランチのモジュール構成とちゃんと噛み合うかを検証できます。`flake.nix` の `checks.${system}` に登録されているのは次の 9 つです。

| 種類 | 中身 |
|---|---|
| ツール類 | `hyprquery` / `hydectl` / `hyde-config` / `hyde-ipc` |
| HyDE 本体と素材 | `hyde` / `code-wallbash` / `Bibata-Modern-Ice` / `Tela-circle-dracula` |
| 素材の衝突検出 | `theme-assets` |

`code-wallbash` は [#58](https://github.com/santamn/hydenix/pull/58) で足しました。`nix flake check` は `checks` に名前があるものしかビルドしないので、`nixosConfigurations` 経由で評価されるだけでは hash の誤りや unzip の失敗に気づけません。

`theme-assets` は `buildEnv` で素材パッケージと既定のテーマ（Catppuccin Mocha / Latte）を 1 つのプロファイルに束ねるだけの check です。`home.packages` が実際にやることと同じなので、`share/icons` に同名で中身の違うディレクトリが 2 つ入る状態を、利用者の `nixos-rebuild` ではなく PR の時点で検出できます。

一方で、テーマパッケージ 58 個そのものや `pokego` / `pyamdgpuinfo` は `packages.${system}` にあっても `checks` には無いため、評価されるだけでビルドはされません。ビルドして初めて表面化する壊れ方は残っています。

`flake-check.yml` には `schedule` がありません。一度は毎週月曜 3 時 UTC の `schedule` を足しましたが、その変更を [#10](https://github.com/santamn/hydenix/pull/10) にまとめ直したときに外れ、そのままです。HyDE の rev を上げる PR は renovate が作り、その PR の `flake-check` で `hyde` がビルドされるので、HyDE 側の変更で壊れるならその PR が落ちます。経緯は [08-improvements.md](./08-improvements.md) の A-0 を参照してください。

### flint.yml — 依存の重複検査

名前が紛らわしいですが、これはコードの整形（lint）とは無関係です。実行しているのは `nix run github:NotAShelf/flint -- --fail-if-multiple-versions` で、`NotAShelf/flint` は `flake.lock` を解析して同じ依存が複数バージョン混在していないかを調べるツールです。たとえば `nixpkgs` が別々の rev で二重に取り込まれていると、ビルド時に同じパッケージが 2 回コンパイルされて閉包が無駄に膨らむので、それを早期に検知するためのチェックです。ジョブ名が `check-dependencies` になっているのもこのためです。他のワークフローが `nixpkgs=channel:nixos-unstable` で Nix をセットアップしているのに対し、このワークフローだけ `nixpkgs=channel:nixos-25.11` を使っている点は現状のまま記録しておきます。

### typos.yml — スペルチェック

`crate-ci/typos` でリポジトリ全体を検査します。設定ファイルは `.typos.toml` で、中身は `hda` と `thumbnailers` を辞書に追加する 2 行だけです。パスの除外設定は無いので、検査対象を絞る仕組みはありません。[09-fork-workflow.md](./09-fork-workflow.md) が日本語コメントと `docs-ja/` を `ja` ブランチに閉じ込めている理由の一つはここにあり、もし `main` に日本語混じりのファイルを置くと、日本語の中に混ざった英単語がこのチェックに誤検出される可能性があります。

### zizmor.yml — ワークフローの静的解析

`.github/workflows/` 自体をセキュリティ観点で静的解析するワークフローです。`zizmorcore/zizmor-action` を使い、`security-events: write` 権限で結果を SARIF として GitHub にアップロードします（`advanced-security: false` なので GitHub Advanced Security 機能を前提としない設定です）。zizmor が典型的に検出するのは、Action の参照が SHA 固定になっていない、`pull_request_target` を安全でない形で使っている、権限が必要以上に広い、といった類の問題です。後述する共通の設計はおおむね zizmor が指摘し得る観点を先回りして守る形になっています。

### 整形（nix fmt）は CI に含まれていない

`flake.nix` の `checks.${system}` を見ると次のようになっています。

```nix
checks.${system} = {
  # "formatting" = treefmtEval.config.build.check inputs.self;
  inherit (pkgs) hyprquery hydectl hyde-config hyde-ipc hyde code-wallbash Bibata-Modern-Ice Tela-circle-dracula;
  theme-assets = pkgs.buildEnv {...};
};
```

コメントアウトされた行の上には整形は CI 側（flint / treefmt）に任せる方針という注記がありますが、実際に `.github/workflows/` を見る限り `treefmt` や `nix fmt` を呼び出しているワークフローは存在しません。`flint.yml` が検査しているのは前述の通り依存の重複であり、整形チェックの代わりにはなっていません。そのため `alejandra` / `deadnix` / `statix`（`treefmt.nix` で束ねられているフォーマッタと linter）による整形は、現状 CI では検査されておらず、手元で `nix fmt` を実行するかレビューで気づくかに委ねられています。[09-fork-workflow.md](./09-fork-workflow.md) の PR チェックリストに整形を通すことが挙がっているのは、CI が強制しているという意味ではなく、PR を送る側が守るべき手順として書かれているものです。

## 自動更新系のワークフロー

依存関係やテーマを最新に保つための 3 つの仕組みです。

### renovate.yml — Nix レベルの依存更新

2 つのジョブがあります。`renovate-config-validator` はどのトリガーでも動き、`renovate-config-validator --strict` で `.github/renovate.json` の妥当性だけを検査します。`renovate-local` が実際に renovate 本体を動かすジョブで、`workflow_dispatch` と毎週日曜 0 時 UTC の `schedule` に加えて `pull_request` でも起動しますが、`pull_request` のときは `RENOVATE_DRY_RUN=full` を強制するので、PR 上で動いても実際に PR を作ったりマージしたりはしません。ただし、この dry-run は PR の `renovate.json` を検証していません。renovate はリポジトリ設定を API 経由でデフォルトブランチから読み、`configurationFile` で渡したチェックアウト済みのファイルはグローバル設定として扱われるだけなので、その上に `main` の設定が被さります（2026-09-10 に [#66](https://github.com/santamn/hydenix/pull/66) で確認）。PR の設定を見ているのは `renovate-config-validator` だけで、それもスキーマの検査までです。設定変更の中身を確かめたいときは、手元で `RENOVATE_CONFIG_FILE=.github/renovate.json RENOVATE_PLATFORM=local renovate --dry-run=extract --print-config` を実行してプリセット解決後の値を見ます。このジョブは `environment: renovate` を指定しており、GitHub 側の Environment 保護ルール（設定されていればレビュー必須などの制限）を経由しないと `RENOVATE_TOKEN` に到達できないようになっています。`docker-cmd-file: .github/renovate-entrypoint.sh` は renovate の実行コンテナに Nix が入っていないための仕込みで、root で起動した直後に `/nix` を用意して `ubuntu` ユーザーに切り替え、シングルユーザーモードで Nix をインストールしてから本来の `renovate` コマンドに処理を渡します。これが必要なのは `.github/renovate.json` の `postUpgradeTasks` が `nix run` や `nix flake lock` を直接呼び出す構成になっているためです。

`renovate.json` は `enabledManagers` を `nix` と `custom.regex` だけに絞っています（GitHub Actions のバージョンは Dependabot の担当です）。`customManagers` は 2 種類あります。

1 つ目（`nix-raw-pkgs`）は `pkgs/**/*.nix` の中の `fetchFromGitHub { owner = "..."; repo = "..."; rev = "..."; }` という形を正規表現で拾い、GitHub のリリースと突き合わせて新しいタグがあれば `rev` を書き換えます。そのあと `postUpgradeTasks` で `nix run .#update-hashes` を実行し、古くなった `hash` を nix に計算し直させます。`update-hashes` は `flake.nix` の `apps` にあるコマンドで、引数を取りません。flake の `packages` のうち `src` が fetcher のものだけを集め、それぞれを `nix-update --version=skip` に渡します。`version` は各パッケージが `lib.removePrefix "v" src.rev` で `rev` から導いているので、renovate が書き換えるのは `rev` の 1 か所で済みます。

以前はここで `nix-update <パッケージ名>` を呼んでいましたが、渡していたのは renovate の `depName`、つまり GitHub のリポジトリ名でした。`HyDE` を nix の属性名として渡しても `pkgs.hyde` には当たりません。しかも `HyDE-Project/HyDE` は `hyde` と `hyde-diff-upstream` の両方の取得元なので、リポジトリ名から属性名は 1 つに決まりません。[#61](https://github.com/santamn/hydenix/pull/61) で、renovate は `rev` を書き換えるだけにして、どの hash が古くなったかは nix が判断する形に分けました。`renovate.yml` の `RENOVATE_ALLOWED_COMMANDS` も、この `nix run .#update-hashes` と `nix flake lock` の 2 つだけを許しています。

2 つ目（`nix-flake-inputs`）は `flake.nix` の `<入力名>.url = "github:owner/repo/vX.Y.Z";` という形を拾い、更新が見つかると該当ディレクトリで `nix flake lock` を実行します。パターンを semver 形式のタグに絞ってあるので、今これに当たるのは `hyprland.url = "github:hyprwm/Hyprland/v0.56.2"` だけです。以前は `nixpkgs` の rev 直書きもパターンに一致していましたが、rev は semver ではないので更新が出ることはありませんでした。

`ignorePaths` で `hydenix-themes/` と `template/` と `demo/` を除外しているのは、テーマは `update-branch-pins.yml` が別の方法で進めており、`template/` と `demo/` は利用者向けの雛形であって renovate の更新対象ではないためです。

`lockFileMaintenance` は `flake.lock` の全入力を更新する PR を作る設定で、nixpkgs や home-manager はここで進みます。`schedule` を空にしてあるのは、`config:best-practices` が入れる `:maintainLockFilesWeekly` の窓（`schedule:earlyMondays`、月曜 0〜3 時）がワークフローの起動時刻（日曜 0 時 UTC）と重ならず、ロック更新のブランチが一度も作られなかったためです。空にすると、いつ走るかはワークフローの cron だけで決まります。`automerge: true` なので、PR のチェックが通れば renovate がマージします。renovate の PR は `RENOVATE_TOKEN` で作られるので、`flake-check.yml` などの PR ゲートは普通に走ります。

以前は `update-flake-lock.yml` が同じ日曜 0 時 UTC に `flake.lock` を更新していました。`flake.nix` の `nixpkgs.url` に rev を直書きしていたので `nix flake update` では動かせず、`scripts/update-flake-lock.sh` が URL を `nixos-unstable` に書き換えて更新し、解決された rev を `flake.nix` に書き戻すという手順を踏んでいました。[#66](https://github.com/santamn/hydenix/pull/66) で `nixpkgs.url` をブランチ指定に変えてこの手順を不要にし、ワークフローごと削除しています。利用者に届く nixpkgs は `template/flake.nix` の `nixpkgs.follows = "hydenix/nixpkgs"` を通じて `flake.lock` の rev で決まるので、`flake.nix` 側の固定には意味がありませんでした。なお、このワークフローはフォークしてから一度も PR を作れていません。後述するリポジトリ設定のせいで、毎週 `GitHub Actions is not permitted to create or approve pull requests` で失敗していました。

### update-branch-pins.yml — ブランチピンの更新

毎日 0 時 UTC に起動し、`nix run .#update-branch-pins` を実行します。ブランチピンと呼んでいるのは、ブランチを追いながら `rev` は commit で固定している箇所のことです。今はテーマ 58 個と、`hyde-diff-upstream` が比較に使う HyDE master のビルド（`hyde-diff-upstream.hyde-master`）がこれに当たります。

アプリは各ピンを nix-update に渡します。追うブランチはテーマなら `mkTheme` の `branch` 引数に、`hyde-master` なら `passthru.updateBranch = "master"` に書いてあり、`null` ならリポジトリの既定ブランチです。nix-update は `--version=branch`（ブランチ名があれば `--version=branch=<名前>`）でブランチの先頭を解決し、`rev` と `sha256` をまとめて書き換えます。nix-update はパッケージを flake の属性パスで受け取るので、テーマの集合は `legacyPackages.x86_64-linux.hydenix-themes` として公開してあります。`packages` には derivation しか置けないからです。

ブランチを解決できないピンがあっても残りは続け、最後に失敗したものを並べて非ゼロで終わります。ワークフローはこのステップに `continue-on-error: true` を付けて先に PR を作り、`gh pr merge --rebase` でマージしてから、最後のステップで失敗を表に出します。更新できたピンは `main` に入り、壊れた追跡先はジョブの失敗として残ります。PR に入れるファイルは `add-paths` で `pkgs/hydenix-themes/*.nix` と `pkgs/hyde-diff-upstream/default.nix` に絞っています。

前身の `update-themes.yml` と `scripts/update-themes.sh` は、`rev` がコミットハッシュなら最新とみなす分岐のせいで、一度も `rev` を進めていませんでした（[08-improvements.md](./08-improvements.md) の B-7）。[#67](https://github.com/santamn/hydenix/pull/67) で nix-update を使う形に作り直し、[#69](https://github.com/santamn/hydenix/pull/69) で HyDE master のピンを加えたときに今の名前へ改めています。

### dependabot.yml — GitHub Actions 自体の更新

これだけは独立したワークフローファイルではなく、GitHub がネイティブに提供する Dependabot の設定です。`package-ecosystem: github-actions` だけを対象にしており、`.github/workflows/*.yml` の中の `uses: owner/action@<sha>` を毎日 0 時 UTC に確認して新しいバージョンが出ていれば PR を作ります。コミット履歴に並ぶ `chore(deps): bump zizmorcore/zizmor-action from 0.6.0 to 0.6.1` のような PR がこれです。`cooldown.default-days: 7` によってリリースから 7 日は様子を見てから提案し、`open-pull-requests-limit: 10` で同時に開く PR 数の上限を設けています。renovate が Nix レベルの依存（flake input とパッケージのピン）を担当するのに対し、dependabot は Actions のバージョンだけを担当するという住み分けです。`lockFileMaintenance` や `update-branch-pins.yml` と違って、Dependabot の PR を自動でマージする仕組みはありません。作られた PR は他の PR と同じようにマージを待ちます。

### GITHUB_TOKEN で作る PR の制約

自動更新 PR を作る仕組みのうち、renovate は別途用意した `secrets.RENOVATE_TOKEN` を使い、`update-branch-pins.yml` は `secrets.GITHUB_TOKEN` を使います。GitHub Actions では、`GITHUB_TOKEN` で行った push や PR 作成は他のワークフローの `push` / `pull_request` を起動しません。つまり `update-branch-pins.yml` の PR には `flake-check.yml` も `typos.yml` も走らず、テーマの更新は `nix flake check` を通らないまま `main` に入ります。

同じ理由で `gh pr merge --auto`（auto-merge）も使えません。待つチェックが 1 つも無い PR は作られた時点で clean な状態で、そこへ auto-merge を有効にしようとするとエラーになります。このリポジトリでは auto-merge 自体も無効です。[#52](https://github.com/santamn/hydenix/pull/52) で `gh pr merge` を直接呼ぶ形に改め、作成直後は mergeability の計算が終わっていないことがあるので 15 秒おきに 5 回まで再試行しています。ブランチ保護（ruleset `main`）が必須のステータスチェックを設定していないのもこのためで、設定すると `GITHUB_TOKEN` の PR は来ないチェックを待ち続けることになります。

`GITHUB_TOKEN` で PR を作るには、Settings → Actions → General の「Allow GitHub Actions to create and approve pull requests」を有効にしておく必要があります。フォークした時点では無効で、`update-flake-lock.yml` はこのせいで失敗し続けていました。2026-09-09 に有効にしています。renovate と Dependabot の PR はどちらの制約も受けず、通常の `pull_request` トリガーを起動します。

## ドキュメントの公開（pages.yml）

`docs/` を `mdbook build docs` でビルドするところまでは `push`・`pull_request`・`workflow_dispatch` のいずれでも実行され、ビルドが通るかどうかだけを確認します。実際に `peaceiris/actions-gh-pages` で公開する最後のステップには `if: ${{ github.ref == 'refs/heads/main' }}` という条件が付いており、`main` への push のときだけ動きます。公開先はワークフローを実行しているリポジトリ自身の `gh-pages` ブランチと Pages サイトです。

上流のアーカイブに伴い、このリポジトリでも GitHub Pages を有効化しました（`gh-pages` ブランチのルートを公開）。[README.md](./README.md) からのリンクも <https://santamn.github.io/hydenix/> を指すように書き換えてあります。

## すべてのワークフローに共通する設計

個々のワークフローを横断して、いくつか一貫した書き方があります。

`actions/checkout` や `cachix/install-nix-action` などの Action は、タグではなく完全な commit SHA で固定し、末尾に `# v7.0.1` のようにバージョン番号をコメントで添える形に統一されています。タグは指す先が後から変わり得ますが、SHA 固定であればワークフローが実際に実行する内容が変わらないことを保証できます。

`actions/checkout` の呼び出しはほぼ全てで `persist-credentials: false` を指定しています。これを指定しないと、チェックアウト後の作業ディレクトリに `GITHUB_TOKEN` を使った git の認証情報が残り、以降のステップで実行される任意のコマンドがそれを使って push できる状態になってしまいます。

権限は多くのワークフローでファイル冒頭の `permissions: {}` を起点にし、必要なジョブだけがその中で個別に権限を書き足す形です。例外もあり、`pages.yml` はジョブが 1 つしかないためワークフロー冒頭で直接必要な権限を宣言しており、`update-branch-pins.yml` にはワークフロー冒頭の `permissions` 自体が無くジョブ側だけで宣言しています。結果として実質的な権限の広さはどれも必要最小限に収まっていますが、書き方の統一という意味では完全に揃ってはいません。

シークレットは基本的に GitHub が自動発行する `GITHUB_TOKEN` で足りていますが、`renovate-local` ジョブだけは `RENOVATE_TOKEN` という別のトークンを使い、さらに `environment: renovate` による保護を経由します。

これらの約束事は `zizmor.yml` が継続的に検査している観点とおおむね一致しています。新しくワークフローを足すときや既存のものを書き換えるときは、この一覧を踏まえたうえで zizmor の結果も確認すると安全です。
