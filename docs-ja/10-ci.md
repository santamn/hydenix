# 10. CI の仕組み

このリポジトリで GitHub Actions が何をしているかをまとめます。

## 全体像

CI の定義は `.github/workflows/` 以下にある 9 個のワークフローファイルと、依存更新を担当する `.github/dependabot.yml`・`.github/renovate.json` に分かれています。実行基盤は GitHub Actions で、`nix flake check` のような Nix 由来のチェックも含めてすべてこの上で動きます。検証系のワークフローは florianvazelle/hydenix から引き継いだものに、変更されたファイルを見て実行を省く仕組みを足しています。依存更新まわりと `flake.nix` の `checks` はこのフォークで組み替えました。

上流はアーカイブされたので、これらのワークフローが動いているのはもうこのリポジトリだけです。`renovate.yml` / `update-branch-pins.yml` が作る自動更新 PR も、`pages.yml` が公開する GitHub Pages も、すべてこのリポジトリ自身に対して作られます。ボットの PR は、必須チェックが通れば自動でマージされます。人がマージするまで残るのは、HyDE のリリースを上げる renovate の PR と、チェックが失敗した PR です。放置すると誰も拾いません。

これらの仕組みの大半（treefmt・typos・zizmor・renovate・mdbook での Pages 公開）はもともとの本家である richen604/hydenix にはなく、florianvazelle 氏がフォークした際に追加したものです。経緯の要約は [README.md](./README.md) の本家からの主な変更点を参照してください。ここではその中身を実際のワークフロー定義に沿って詳しく見ていきます。

PR を検証するワークフローの `on:` は `workflow_dispatch` と `pull_request` が基本で、`push` を持つのは `flake-check.yml` と `pages.yml` の 2 つだけです（どちらも `main` ブランチのみ）。そのため `ja` ブランチへの push では CI は起動しません。docs-ja/ を読みながら CI の挙動が気になったときは、常に `main` 相当の内容に対して実行されていると考えてください。

## ワークフロー一覧

| ファイル | 主なトリガー | 役割 |
|---|---|---|
| `commit-lint.yml` | pull_request | PR に含まれるコミットメッセージが Conventional Commits に従っているか確認する |
| `flake-check.yml` | workflow_dispatch, push（main）, pull_request | ルートと `template/` の flake を評価し、`checks` に登録されたものをビルドする。`docs/`・`.github/`・ルートの `*.md` だけの変更では省く |
| `flint.yml` | workflow_dispatch, pull_request | `flake.lock` の中で同じ依存が複数バージョン混在していないか調べる。PR では `flake.lock` が変わったときだけ |
| `typos.yml` | workflow_dispatch, pull_request | リポジトリ全体のスペルミスをチェックする |
| `zizmor.yml` | workflow_dispatch, pull_request | ワークフロー定義自体をセキュリティ観点で静的解析する。PR では `.github/workflows/` か `dependabot.yml` が変わったときだけ |
| `renovate.yml` | workflow_dispatch, schedule（毎週日曜 0 時 UTC）, pull_request | 依存更新 PR（`flake.lock` の更新を含む）を作成する。PR では renovate の設定と起動方法が変わったときだけ検証する |
| `update-branch-pins.yml` | workflow_dispatch, schedule（毎週日曜 0 時 UTC） | テーマ・HyDE master・hyprquery の commit 固定を、追っているブランチの先頭へ進める PR を作り、auto-merge を有効にする |
| `dependabot-auto-merge.yml` | workflow_dispatch, schedule（毎日 3 時 UTC） | 開いている Dependabot の PR に auto-merge を有効にする |
| `pages.yml` | workflow_dispatch, push（main）, pull_request | `docs/` を mdbook でビルドし、`main` のときだけ GitHub Pages に公開する。push と PR では `docs/` が変わったときだけ動く |
| `dependabot.yml` | GitHub 側の機構、毎日 | `.github/workflows/` が参照する Action のバージョンを更新する PR を作成する |

以降はこれを 3 つに分けて説明します。PR を検証するもの、スケジュール実行で自動更新 PR を作るもの、ドキュメントを公開するものです。

## PR を検証するワークフロー

`pull_request` イベントで起動する次の 5 つのワークフローが PR を検証します。`main` の ruleset は、これらのジョブに `pages.yml` の `deploy` と `renovate.yml` の `renovate-config-validator` を加えた 7 つを必須チェックにしており、PR はそれが通るまでマージできません。

`commit-lint.yml` と `typos.yml` 以外のワークフローは、先頭の `changes` ジョブで PR が変えたファイルを GitHub の compare API から取得し、関係するファイルが無ければ本体のジョブをスキップします。`on.pull_request.paths` で絞らないのは、ワークフローごと起動しないと必須チェックが待機中のまま残るためです。スキップされたジョブは必須チェックを満たします。`changes` ジョブ自体が失敗したときは、本体のジョブを実行します。

### commit-lint.yml — コミットメッセージのチェック

PR のときだけ起動します。`fetch-depth: 0` で全履歴を取得したうえで `.commitlintrc.json` を `$HOME/.commitlintrc.json` にコピーし、`commitlint --from <base sha> --to <head sha>` で PR に含まれるコミットだけをチェックします。ルールは type が build・chore・ci・docs・feat・fix・perf・refactor・revert・style・test のいずれかであること、先頭行が 72 文字以内であること、末尾にピリオドを置かないこと、type と scope が小文字であることです。書き方の例は [09-fork-workflow.md](./09-fork-workflow.md) にまとまっています。

### flake-check.yml — flake の評価とビルド

ルートの `nix flake check` を実行したあと、`template/` 側でも同じことをします。`template/flake.nix` はふだん `inputs.hydenix.url = "github:santamn/hydenix"` を参照していますが、これをそのまま評価すると変更中のコードではなく `main` の最新を見てしまいます。そこで CI では `sed` で一時的に `path:../` に書き換えてから `nix flake check` を実行し、終わったら `flake.nix` を `git checkout` で戻して `flake.lock` を削除します。`sed` のパターンはこの URL と一字一句一致していないと、エラーにならないまま何も置換しないので、`template/flake.nix` の入力先を変えるときは `flake-check.yml` の `sed` も一緒に直す必要があります。こうすることで、テンプレートが今のブランチのモジュール構成とちゃんと噛み合うかを検証できます。手元で同じ確認をするときは、AGENTS.md にあるとおり `nix flake check ./template --override-input hydenix path:. --no-write-lock-file` を使います。これなら `template/flake.nix` を書き換えず、`template/flake.lock` も残りません。`flake.nix` の `checks.${system}` に登録されているのは次の 10 個です。

| 種類 | 中身 |
|---|---|
| ツール類 | `hyprquery` / `hydectl` / `hyde-config` |
| HyDE 本体と素材 | `hyde` / `code-wallbash` / `Bibata-Modern-Ice` / `Tela-circle-dracula` |
| 生成する設定の検証 | `hyprland-config` / `waybar-includes` |
| 素材の衝突検出 | `theme-assets` |

`nix flake check` は `checks` に名前があるものしかビルドしないので、`nixosConfigurations` 経由で評価されるだけでは hash の誤りやビルドの失敗に気づけません。

`hyprland-config` は、hydenix が書き出す `~/.config/hypr/hyprland.lua` で HyDE の Lua 設定を読み込めるかを確かめる check です。`presets.nix` のプリセット名が `pkgs.hyde` の実ファイルと一致するかを比べ、activation と同じ `hyde-shell <セレクタ> --set` を実行したうえで、`HYPRLAND_CONFIG` を指定した起動と指定しない起動の両方で `Hyprland --verify-config` を通します。`waybar-includes` は、`waybar.nix` が HyDE の `waybar.py` で `includes.json` を生成するビルドそのものです。HyDE の更新で `waybar.py` の import や関数名が変われば、ここでビルドが失敗します。どちらもデモ構成の `homeConfigurations.default` から作ります。

`theme-assets` は、単体の素材パッケージ（`Bibata-Modern-Ice` / `Tela-circle-dracula`）と、既定のテーマ（Catppuccin Mocha / Latte）から作った `hydenix-theme-assets` の `altIcons` を、`buildEnv` で 1 つのプロファイルに束ねる check です。`home.packages` が実際にやることと同じなので、`share/icons` に同名で中身の違うディレクトリが 2 つ入る状態を、利用者の `nixos-rebuild` ではなく PR の時点で検出できます。`altIcons` はテーマ素材をまとめたツリー全体を参照するので、そのまとめる処理もここでビルドされます。

一方で、既定の 2 つ以外のテーマパッケージや `pyamdgpuinfo` は `checks` に無いため、CI ではビルドされません。ビルドして初めて表面化する不具合は、CI では見つからないまま残ります。

`flake-check.yml` には `schedule` がありません。HyDE の rev を上げる PR は renovate が作り、その PR の `flake-check` で `hyde` がビルドされるので、HyDE 側の変更でビルドが通らなくなるなら、その PR のチェックが失敗します。

### flint.yml — 依存の重複チェック

名前が紛らわしいですが、これはコードの整形（lint）とは無関係です。実行しているのは `nix run github:NotAShelf/flint -- --fail-if-multiple-versions` で、`NotAShelf/flint` は `flake.lock` を解析して同じ依存が複数バージョン混在していないかを調べるツールです。たとえば `nixpkgs` が別々の rev で二重に取り込まれていると、ビルド時に同じパッケージが 2 回コンパイルされて閉包が無駄に膨らむので、それを早期に検知するためのチェックです。ジョブ名が `check-dependencies` になっているのもこのためです。PR では、`changes` ジョブが `flake.lock` か `flint.yml` の変更を見つけたときだけ実行します。

### typos.yml — スペルチェック

`crate-ci/typos` でリポジトリ全体のスペルをチェックします。設定ファイルは `.typos.toml` で、中身は `hda` と `thumbnailers` を辞書に追加する 2 行だけです。パスの除外設定は無いので、チェック対象を絞る仕組みはありません。[09-fork-workflow.md](./09-fork-workflow.md) が日本語コメントと `docs-ja/` を `ja` ブランチに閉じ込めている理由の1つはここにあり、もし `main` に日本語混じりのファイルを置くと、日本語の文中にある英単語がこのチェックに誤検出される可能性があります。

### zizmor.yml — ワークフローの静的解析

`.github/workflows/` 自体をセキュリティ観点で静的解析するワークフローです。`zizmorcore/zizmor-action` を `advanced-security: false` で使うので、結果は SARIF として Security タブへ送られず、ジョブのログに出ます。検出があると zizmor が 11〜14 の終了コードを返し、ジョブが失敗します。ジョブに付けた `security-events: write`（コメントでは SARIF のアップロード用と説明）は、この設定では使われません。PR では `.github/workflows/` か `.github/dependabot.yml` が変わったときだけ実行します。zizmor が典型的に検出する問題には、Action の参照が SHA 固定になっていないこと、`pull_request_target` を安全でない形で使っていること、権限が必要以上に広いことなどがあります。後述する共通の設計はおおむね zizmor が指摘し得る観点を先回りして守る形になっています。

### 整形（nix fmt）は CI に含まれていない

`flake.nix` の `checks.${system}` を見ると次のようになっています。

```nix
checks.${system} = {
  # "formatting" = treefmtEval.config.build.check inputs.self;
  inherit (pkgs) hyprquery hydectl hyde-config hyde code-wallbash Bibata-Modern-Ice Tela-circle-dracula;
  hyprland-config = ...;
  waybar-includes = ...;
  theme-assets = pkgs.buildEnv {...};
};
```

コメントアウトされた行の上の注記にもあるとおり、`.github/workflows/` に `treefmt` や `nix fmt` を呼び出すワークフローはありません。`flint.yml` が調べているのは前述の通り依存の重複であり、整形チェックの代わりにはなっていません。そのため `alejandra` / `deadnix` / `statix`（`treefmt.nix` で束ねられているフォーマッタと linter）による整形は、現状 CI ではチェックされておらず、手元で `nix fmt` を実行するかレビューで気づくかに委ねられています。AGENTS.md が push の前に CI と同じチェックに加えて `nix fmt` を実行するよう求めているのも、[09-fork-workflow.md](./09-fork-workflow.md) の PR チェックリストに整形を通すことが挙がっているのも、CI が強制しているからではなく、PR を送る側が守るべき手順だからです。

## 自動更新系のワークフロー

依存関係やテーマを最新に保つための 4 つの仕組みです。

### renovate.yml — Nix レベルの依存更新

3 つのジョブがあります。`changes` は PR のときだけ動き、変更されたファイルから残りの 2 つを動かすかを決めます。`renovate-config-validator` は PR で `.github/renovate.json` か `renovate.yml` が変わったときだけ動き、`renovate-config-validator --strict` で `.github/renovate.json` の妥当性だけを検証します。`renovate-local` が実際に renovate 本体を動かすジョブで、`workflow_dispatch` と毎週日曜 0 時 UTC の `schedule` で起動します。PR では `.github/renovate-entrypoint.sh` か `renovate.yml` が変わったときだけ動き、`RENOVATE_DRY_RUN=full` を強制するので、実際に PR を作ったりマージしたりはしません。Dependabot が起動した実行は `RENOVATE_TOKEN` を読めないので、`github.actor` が `dependabot[bot]` のときは `renovate-local` を動かしません。

この dry-run は PR の `renovate.json` を検証していません。renovate はリポジトリ設定を API 経由でデフォルトブランチから読むためです（2026-09-10 に [#66](https://github.com/santamn/hydenix/pull/66) で確認）。PR 上の dry-run で確かめられるのは renovate の起動方法（`renovate.yml` と `renovate-entrypoint.sh`）だけです。PR の設定を見ているのは `renovate-config-validator` だけで、それもスキーマの検証までです。設定変更の中身を確かめたいときは、手元で `RENOVATE_CONFIG_FILE=.github/renovate.json RENOVATE_PLATFORM=local renovate --dry-run=extract --print-config` を実行してプリセット解決後の値を見ます。`renovate-local` は `environment: renovate` を指定しているので、GitHub 側の Environment 保護ルール（設定されていればレビュー必須などの制限）を経由しないと `RENOVATE_TOKEN` を読み出せません。`docker-cmd-file: .github/renovate-entrypoint.sh` は renovate の実行コンテナに Nix が入っていないための仕込みで、root で起動した直後に `/nix` を用意して `ubuntu` ユーザーに切り替え、シングルユーザーモードで Nix をインストールしてから本来の `renovate` コマンドに処理を渡します。これが必要なのは `.github/renovate.json` の `postUpgradeTasks` が `nix run` や `nix flake lock` を直接呼び出す構成になっているためです。

`renovate.json` は `enabledManagers` を `nix` と `custom.regex` だけに絞っています（GitHub Actions のバージョンは Dependabot の担当です）。`customManagers` は 2 種類あります。

1 つ目（`nix-raw-pkgs`）は `pkgs/**/*.nix` の中の `fetchFromGitHub { owner = "..."; repo = "..."; rev = "..."; }` という形を正規表現で拾い、GitHub のリリースと比べて新しいタグがあれば `rev` を書き換えます。今タグで固定しているのは `hyde`・`hydectl`・`hyde-config`・`code-wallbash`・`pyamdgpuinfo` です。そのあと `postUpgradeTasks` で `nix run .#update-hashes` を実行し、古くなった `hash` を nix に計算し直させます。`update-hashes` は `flake.nix` の `apps` にあるコマンドで、引数を取りません。flake の `packages` のうち `src` が fetcher のものだけを集め、それぞれを `nix-update --version=skip` に渡します。タグで固定したパッケージは `version` を `lib.removePrefix "v" src.rev` で `rev` から導いているので、renovate が書き換えるのは `rev` の 1 か所で済みます。

`renovate.yml` の `RENOVATE_ALLOWED_COMMANDS` は、この `nix run .#update-hashes` と `nix flake lock` の 2 つだけを許しています。

2 つ目（`nix-flake-inputs`）は `flake.nix` の `<入力名>.url = "github:owner/repo/vX.Y.Z";` という形を拾い、更新が見つかると該当ディレクトリで `nix flake lock` を実行します。パターンを semver 形式のタグに絞ってあり、今の `flake.nix` の入力はどれもブランチを指しているので、この設定に当たるものはありません。

`ignorePaths` で `hydenix-themes/`・`template/`・`demo/` を除外しているのは、テーマは `update-branch-pins.yml` が別の方法で進めており、`template/` と `demo/` は利用者向けの雛形であって renovate の更新対象ではないためです。

`lockFileMaintenance` は `flake.lock` の全入力を更新する PR を作る設定で、nixpkgs や home-manager はここで進みます。`schedule` を空にしてあるのは、`config:best-practices` が入れる `:maintainLockFilesWeekly` の窓（`schedule:earlyMondays`、月曜 0〜3 時）がワークフローの起動時刻（日曜 0 時 UTC）と重ならず、そのままではロック更新のブランチが作られないためです。空にすると、いつ実行されるかはワークフローの cron だけで決まります。`automerge: true` なので、PR のチェックが通れば renovate がマージします。renovate の PR は `RENOVATE_TOKEN` で作られるので、`flake-check.yml` などの PR 向けチェックは通常どおり実行されます。nixpkgs が Hyprland を HyDE の対応していない major.minor に上げると、`modules/system/system.nix` の assertion でこの PR の `flake-check` が落ち、マージされずに残ります。その扱いは `docs/src/contributing.md` の Updating the supported Hyprland version に書いてあります。

`automerge: true` はトップレベルにもあるので、`rev` を上げる PR も必須チェックが通れば renovate がマージします。例外は `packageRules` で `automerge: false` にしている HyDE（`HyDE-Project/HyDE`）のリリースです。HyDE のリリースでは hydenix が組み込んでいる HyDE の設定そのものが変わるので、人がレビューしてからマージします。また GitHub のリリースを元にした更新は、`minimumReleaseAge: "7 days"` でリリースから 7 日たつまで提案しません。Dependabot の cooldown と同じ日数です。

### update-branch-pins.yml — ブランチピンの更新

毎週日曜 0 時 UTC に起動し、`nix run .#update-branch-pins` を実行します。ブランチピンと呼んでいるのは、ブランチを追いながら `rev` は commit で固定している箇所のことです。今はテーマ 58 個と、`hyde-diff-upstream` が比較に使う HyDE master のビルド（`hyde-diff-upstream.hyde-master`）、`hyprquery` の 3 種類です。HyDE のテーマ切り替えが使う `--dump` と `--export lua` は hyprquery の `main` にしか無くリリースされていないので、hyprquery はタグではなく `main` を追っています。

アプリは各ピンを nix-update に渡します。追うブランチはテーマなら `mkTheme` の `branch` 引数に、`hyde-master` なら `passthru.updateBranch = "master"` に、`hyprquery` なら `passthru.updateBranch = "main"` に書いてあり、`null` ならリポジトリの既定ブランチです。nix-update は `--version=branch`（ブランチ名があれば `--version=branch=<名前>`）でブランチの先頭を解決し、`rev` と `sha256` をまとめて書き換えます。nix-update はパッケージを flake の属性パスで受け取るので、テーマの集合は `legacyPackages.x86_64-linux.hydenix-themes` として公開してあります。`packages` には derivation しか置けないからです。

ブランチを解決できないピンがあっても残りは続け、最後に失敗したものをログ付きで並べて非ゼロで終わります。ワークフローはこのステップの失敗を出力 `failed` に記録するだけで先へ進み、`RENOVATE_TOKEN` で PR を作って `gh pr merge --auto --rebase` で auto-merge を有効にします。マージは必須チェックが通った時点で GitHub が行います。最後のステップは、失敗があればログの `could not update:` 以降をエラーの注釈とジョブのサマリーに書き出し、ジョブを失敗させます。更新できたピンは `main` に入り、ブランチを解決できなかった追跡先はジョブの失敗として残ります。PR に入れるファイルは `add-paths` で `pkgs/hydenix-themes/*.nix`、`pkgs/hyde-diff-upstream/default.nix`、`pkgs/hyprquery/default.nix` に絞っています。

### dependabot.yml — GitHub Actions 自体の更新

これだけは独立したワークフローファイルではなく、GitHub がネイティブに提供する Dependabot の設定です。`package-ecosystem: github-actions` だけを対象にしており、`.github/workflows/*.yml` の中の `uses: owner/action@<sha>` を毎日 0 時 UTC に確認して新しいバージョンが出ていれば PR を作ります。コミット履歴に並ぶ `chore(deps): bump zizmorcore/zizmor-action from 0.6.0 to 0.6.1` のような PR がこれです。`cooldown.default-days: 7` によってリリースから 7 日は様子を見てから提案し、`open-pull-requests-limit: 10` で同時に開く PR 数の上限を設けています。renovate が Nix レベルの依存（flake input とパッケージのピン）を担当するのに対し、dependabot は Actions のバージョンだけを担当するという住み分けです。Dependabot の PR のマージは、次の `dependabot-auto-merge.yml` が受け持ちます。

### dependabot-auto-merge.yml — Dependabot の PR の自動マージ

毎日 3 時 UTC（Dependabot が 0 時に動いた後）に起動し、`app/dependabot` が作った開いている PR すべてに `gh pr merge --auto --merge` で auto-merge を有効にします。マージは必須チェックが通った時点で GitHub が行います。

Dependabot の PR の `pull_request` イベントで同じことをしないのは、使えるトークンが無いためです。Dependabot の PR は `.github/workflows/` を書き換えるので、`GITHUB_TOKEN` ではその PR の auto-merge を有効にできません。また Dependabot が起動した実行は Dependabot 用のシークレットしか読めないので、`RENOVATE_TOKEN` も使えません。そこでスケジュール実行から、`environment: renovate` を通して `RENOVATE_TOKEN` を使います。このトークンには workflow スコープ（fine-grained token なら Workflows の書き込み権限）が必要です。

### GITHUB_TOKEN で作る PR の制約

ボットの PR を作る・マージする仕組み（renovate、`update-branch-pins.yml`、`dependabot-auto-merge.yml`）は、どれも別途用意した `secrets.RENOVATE_TOKEN` を使い、`GITHUB_TOKEN` はチェックアウトにしか使いません。2026 年 6 月から、ワークフローが `GITHUB_TOKEN` で作成・更新した PR の `pull_request` 実行は、書き込み権限を持つ人が承認するまで保留されるようになったためです。保留中は必須チェックが揃わないので、auto-merge も進みません。`RENOVATE_TOKEN` で作った PR では、人が作った PR と同じくすぐにチェックが始まります。

`main` の ruleset は PR を経由しない変更を受け付けず、7 つの必須チェックが通るまでマージを止めます。リポジトリの設定で auto-merge は有効にしてあり、`update-branch-pins.yml` と `dependabot-auto-merge.yml` は `gh pr merge --auto` でマージを GitHub に任せます。

## ドキュメントの公開（pages.yml）

`deploy` ジョブは、`docs/` か `pages.yml` が変わった push と PR、それに `workflow_dispatch` で実行され、`docs/` を `mdbook build docs` でビルドします。実際に `peaceiris/actions-gh-pages` で公開する最後のステップには `if: ${{ github.ref == 'refs/heads/main' }}` という条件が付いており、`main` への push（と `main` で実行した `workflow_dispatch`）のときだけ動きます。PR ではビルドが通るかどうかだけを確認します。公開先はワークフローを実行しているリポジトリ自身の `gh-pages` ブランチと Pages サイトです。

このリポジトリの Pages は `gh-pages` ブランチのルートを公開する設定で、サイトは <https://santamn.github.io/hydenix/> です。

## すべてのワークフローに共通する設計

個々のワークフローを横断して、いくつか一貫した書き方があります。

`actions/checkout` や `cachix/install-nix-action` などの Action は、タグではなく完全な commit SHA で固定し、末尾に `# v7.0.1` のようにバージョン番号をコメントで添える形に統一されています。タグは指す先が後から変わり得ますが、SHA 固定であればワークフローが実際に実行する内容が変わらないことを保証できます。

`actions/checkout` の呼び出しはすべて `persist-credentials: false` を指定しています。これを指定しないと、チェックアウト後の作業ディレクトリに `GITHUB_TOKEN` を使った git の認証情報が残り、以降のステップで実行される任意のコマンドがそれを使って push できる状態になってしまいます。

権限はすべてのワークフローでファイル冒頭の `permissions: {}` を起点にし、必要なジョブだけがその中で個別に権限を書き足す形です。`changes` ジョブは compare API を読むための `contents: read`、`pages.yml` の `deploy` は `gh-pages` へ push するための `contents: write`、`zizmor` は `security-events: write` を持ちます。`RENOVATE_TOKEN` で書き込む `renovate-local` と `update-branch-pins` は、`GITHUB_TOKEN` にはチェックアウト用の `contents: read` しか与えていません。

シークレットは基本的に GitHub が自動発行する `GITHUB_TOKEN` で足りていますが、`renovate-local`・`update-branch-pins`・`dependabot-auto-merge` の 3 つのジョブは `RENOVATE_TOKEN` という別のトークンを使い、どれも `environment: renovate` を経由して読み出します。

これらの約束事は `zizmor.yml` が継続的にチェックしている観点とおおむね一致しています。新しくワークフローを足すときや既存のものを書き換えるときは、この一覧を踏まえたうえで zizmor の結果も確認すると安全です。
