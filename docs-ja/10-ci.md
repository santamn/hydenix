# 10. CI の仕組み

このリポジトリと上流で GitHub Actions が何をしているかをまとめます。

## 全体と上流との関係

CI の定義は `.github/workflows/` 以下にある 9 個のワークフローファイルと、依存更新を担当する `.github/dependabot.yml`・`.github/renovate.json` に分かれています。実行基盤は GitHub Actions で、`nix flake check` のような Nix 由来のチェックも含めてすべてこの上で動きます。[09-fork-workflow.md](./09-fork-workflow.md) にある運用ルールの通り `main` は `git merge upstream/main` だけで上流（florianvazelle/hydenix）に追従しており、CI 設定を含めてこのフォーク側で意図的に変更した箇所はないので、以下で説明する内容はそのまま上流のリポジトリにも当てはまります。ただし GitHub Actions はリポジトリごとに独立して動く仕組みなので、同じワークフロー定義でも実行結果は florianvazelle/hydenix とこのフォークとで別々に存在します。たとえば後述する `pages.yml` が公開する GitHub Pages のサイトや、`renovate.yml` / `update-flake-lock.yml` / `update-themes.yml` が自動作成する PR は、それぞれのワークフローを実行したリポジトリ自身に対して作られます。このフォークの `main` に push した時点でこのフォーク自身の Actions が独立に走るため、上流とは別に自動更新 PR が溜まっていく可能性がある点は運用上意識しておく必要があります。

これらの仕組みの大半（treefmt・typos・zizmor・renovate・mdbook での Pages 公開）はもともとの本家である richen604/hydenix にはなく、florianvazelle 氏がフォークした際に追加したものです。経緯の要約は [README.md](./README.md) の本家からの主な変更点を参照してください。ここではその中身を実際のワークフロー定義に沿って詳しく見ていきます。

ワークフローの `on:` はほとんどが `workflow_dispatch` と `push`（`main` ブランチと tag のみ）と `pull_request` の組み合わせです。`push` の対象が `main` に限られているため、`ja` ブランチへの push はこの条件に一致せず CI は起動しません。docs-ja/ を読みながら CI の挙動が気になったときは、常に `main` 相当の内容に対して実行されていると考えてください。

## ワークフロー一覧

| ファイル | 主なトリガー | 役割 |
|---|---|---|
| `commit-lint.yml` | pull_request | PR に含まれるコミットメッセージが Conventional Commits に従っているか検査する |
| `flake-check.yml` | workflow_dispatch, push（main・tag）, pull_request | ルートと `template/` の flake を評価し、`checks` に登録されたパッケージをビルドする |
| `flint.yml` | workflow_dispatch, push（main・tag）, pull_request | `flake.lock` の中で同じ依存が複数バージョン混在していないか検査する |
| `typos.yml` | workflow_dispatch, push（main・tag）, pull_request | リポジトリ全体のスペルミスを検査する |
| `zizmor.yml` | workflow_dispatch, push（main・tag）, pull_request | ワークフロー定義自体をセキュリティ観点で静的解析する |
| `renovate.yml` | workflow_dispatch, schedule（毎週日曜 0 時 UTC）, pull_request | renovate 設定を検証し、依存更新 PR を作成する |
| `update-flake-lock.yml` | workflow_dispatch, schedule（毎週日曜 0 時 UTC） | `flake.lock` を丸ごと更新する PR を作成する |
| `update-themes.yml` | workflow_dispatch, schedule（毎日 0 時 UTC） | HyDE テーマ素材の rev と sha256 を更新する PR を作成する |
| `pages.yml` | workflow_dispatch, push（main）, pull_request | `docs/` を mdbook でビルドし、`main` への push 時のみ GitHub Pages に公開する |
| `dependabot.yml` | GitHub 側の機構、毎日 | `.github/workflows/` が参照する Action のバージョンを更新する PR を作成する |

以降はこれを 3 つに分けて説明します。PR を検証するもの、スケジュール実行で自動更新 PR を作るもの、ドキュメントを公開するものです。

## PR を検証するワークフロー

`pull_request` イベントで起動する 5 つのワークフローが、実質的に PR をマージする前提条件になっています。

### commit-lint.yml — コミットメッセージの検査

PR のときだけ起動します。`fetch-depth: 0` で全履歴を取得したうえで `.commitlintrc.json` を `$HOME/.commitlintrc.json` にコピーし、`commitlint --from <base sha> --to <head sha>` で PR に含まれるコミットだけを検査します。ルールは type が build・chore・ci・docs・feat・fix・perf・refactor・revert・style・test のいずれかであること、先頭行が 72 文字以内であること、末尾にピリオドを置かないこと、type と scope が小文字であることです。書き方の例は [09-fork-workflow.md](./09-fork-workflow.md) にまとまっています。

### flake-check.yml — flake の評価とビルド

ルートの `nix flake check` を実行したあと、`template/` 側でも同じことをします。`template/flake.nix` はふだん `inputs.hydenix.url = "github:florianvazelle/hydenix"` を参照していますが、これをそのまま評価すると変更中のコードではなく上流の最新リリースを見てしまうので、CI では `sed` で一時的に `path:../` に書き換えてから `nix flake check` を実行し、終わったら `flake.nix` を `git checkout` で戻して `flake.lock` を削除します。こうすることで、テンプレートが今のブランチのモジュール構成とちゃんと噛み合うかを検証できます。注意点として、`flake.nix` の `checks.${system}` に登録されているのは `hyprquery` / `hydectl` / `hyde-config` / `hyde-ipc` の 4 パッケージだけです。`hyde` 本体やテーマパッケージ、`pokego` や `pyamdgpuinfo` などは `packages.${system}` には入っていても `checks` には入っていないため、`nix flake check` では評価されるだけでビルドはされません。実際にビルドされて初めて fetch の失敗などが表面化するので、上流がテーマ素材の tar.gz を削除して壊れたケースのように、CI を素通りしてから利用者の手元で初めて発覚する壊れ方があります。詳しくは [08-improvements.md](./08-improvements.md) の A-0 を参照してください。

### flint.yml — 依存の重複検査

名前が紛らわしいですが、これはコードの整形（lint）とは無関係です。実行しているのは `nix run github:NotAShelf/flint -- --fail-if-multiple-versions` で、`NotAShelf/flint` は `flake.lock` を解析して同じ依存が複数バージョン混在していないかを調べるツールです。たとえば `nixpkgs` が別々の rev で二重に取り込まれていると、ビルド時に同じパッケージが 2 回コンパイルされて閉包が無駄に膨らむので、それを早期に検知するためのチェックです。ジョブ名が `check-dependencies` になっているのもこのためです。他のワークフローが `nixpkgs=channel:nixos-unstable` で Nix をセットアップしているのに対し、このワークフローだけ `nixpkgs=channel:nixos-25.11` を使っている点は現状のまま記録しておきます。

### typos.yml — スペルチェック

`crate-ci/typos` でリポジトリ全体を検査します。設定ファイルは `.typos.toml` で、中身は `hda` と `thumbnailers` を辞書に追加する 2 行だけです。パスの除外設定は無いので、検査対象を絞る仕組みはありません。[09-fork-workflow.md](./09-fork-workflow.md) が日本語コメントと `docs-ja/` を `ja` ブランチに閉じ込めている理由の一つはここにあり、もし `main` に日本語混じりのファイルを置くと、日本語の中に混ざった英単語がこのチェックに誤検出される可能性があります。

### zizmor.yml — ワークフローの静的解析

`.github/workflows/` 自体をセキュリティ観点で静的解析するワークフローです。`zizmorcore/zizmor-action` を使い、`security-events: write` 権限で結果を SARIF として GitHub にアップロードします（`advanced-security: false` なので GitHub Advanced Security 機能を前提としない設定です）。zizmor が典型的に検出するのは、Action の参照が SHA 固定になっていない、`pull_request_target` を安全でない形で使っている、権限が必要以上に広い、といった類の問題です。後述する共通の設計はおおむね zizmor が指摘し得る観点を先回りして守る形になっています。

### 整形（nix fmt）は CI に含まれていない

`flake.nix` の `checks.${system}` を見ると次のようになっています。

```nix
checks.${system} = {
  # "formatting" = treefmtEval.config.build.check inputs.self;
  inherit (pkgs) hyprquery hydectl hyde-config hyde-ipc;
};
```

コメントアウトされた行の上には整形は CI 側（flint / treefmt）に任せる方針という注記がありますが、実際に `.github/workflows/` を見る限り `treefmt` や `nix fmt` を呼び出しているワークフローは存在しません。`flint.yml` が検査しているのは前述の通り依存の重複であり、整形チェックの代わりにはなっていません。そのため `alejandra` / `deadnix` / `statix`（`treefmt.nix` で束ねられているフォーマッタと linter）による整形は、現状 CI では検査されておらず、手元で `nix fmt` を実行するかレビューで気づくかに委ねられています。[09-fork-workflow.md](./09-fork-workflow.md) の PR チェックリストに整形を通すことが挙がっているのは、CI が強制しているという意味ではなく、PR を送る側が守るべき手順として書かれているものです。

## 自動更新系のワークフロー

依存関係やテーマを最新に保つための 4 つの仕組みです。

### renovate.yml — Nix レベルの依存更新

2 つのジョブがあります。`renovate-config-validator` はどのトリガーでも動き、`renovate-config-validator --strict` で `.github/renovate.json` の妥当性だけを検査します。`renovate-local` が実際に renovate 本体を動かすジョブで、`workflow_dispatch` と毎週日曜 0 時 UTC の `schedule` に加えて `pull_request` でも起動しますが、`pull_request` のときは `RENOVATE_DRY_RUN=full` を強制するので、`renovate.json` を変更する PR が来ても実際に PR を作ったりマージしたりすることはなく、設定変更の影響を確認するだけの動きになります。このジョブは `environment: renovate` を指定しており、GitHub 側の Environment 保護ルール（設定されていればレビュー必須などの制限）を経由しないと `RENOVATE_TOKEN` に到達できないようになっています。`docker-cmd-file: .github/renovate-entrypoint.sh` は renovate の実行コンテナに Nix が入っていないための仕込みで、root で起動した直後に `/nix` を用意して `ubuntu` ユーザーに切り替え、シングルユーザーモードで Nix をインストールしてから本来の `renovate` コマンドに処理を渡します。これが必要なのは `.github/renovate.json` の `postUpgradeTasks` が `nix run` や `nix flake lock` を直接呼び出す構成になっているためです。

`renovate.json` は `enabledManagers` を `nix` と `custom.regex` だけに絞っています。`customManagers` は 2 種類あり、1 つ目（`nix-raw-pkgs`）は `pkgs/**/*.nix` の中の `fetchFromGitHub { owner = "..."; repo = "..."; rev = "..."; }` という形を正規表現で拾い、GitHub のリリース情報と突き合わせて新しいバージョンを見つけると `nix run github:Mic92/nix-update -- <パッケージ名> --flake --version <新バージョン>` を実行してピン留めを書き換えます。2 つ目（`nix-flake-inputs`）は `flake.nix` の `<入力名>.url = "github:owner/repo/<rev>";` という形を拾い、更新が見つかると該当ディレクトリで `nix flake lock` を実行します。`hyprland.url = "github:hyprwm/Hyprland/v0.56.1"` のようなバージョンタグ形式の入力はこちらの対象です。`ignorePaths` で `hydenix-themes/` と `template/` と `demo/` を除外しているのは、テーマは仕組みが異なる `update-themes.yml` が別途担当しており、`template/` と `demo/` は利用者向けの雛形であって renovate の更新対象にはなっていないためです。`lockFileMaintenance` も有効になっており、これは次に説明する `update-flake-lock.yml` と役割が重なる部分があります。

### update-flake-lock.yml — flake.lock 全体の更新

毎週日曜 0 時 UTC、renovate と同じ時刻に起動します。`scripts/update-flake-lock.sh` が最初に `flake.nix` の `nixpkgs.url` を `nixos-unstable` ブランチに書き換え、`nix flake update` で `flake.lock` の全入力を最新化し、そのあと `flake.lock` から実際に解決された `nixpkgs` の rev を `jq` で取り出して `flake.nix` に書き戻します。つまり `nixpkgs` は `flake.nix` 側のピンごと更新され、それ以外の入力は `flake.lock` の中だけが更新されます。更新後はルートと `template/`（`flake-check.yml` と同じ `path:../` への書き換えトリック）の両方で `nix flake check` を実行し、成功・失敗にかかわらず出力をキャプチャして PR の本文に埋め込みます。PR は成功・失敗どちらの場合でも `peter-evans/create-pull-request` で作成されますが（`if: always()`）、両方のチェックが通ったときだけ `gh pr merge --auto --squash` で auto-merge を有効化し、どちらかが失敗していればワークフロー自体を最後のステップで意図的に `exit 1` させます。PR は開いたままレビュー待ちにしつつ、ワークフローの成否は正直に失敗として表示する、という組み合わせです。

### update-themes.yml — テーマ素材の更新

毎日 0 時 UTC に起動します。`scripts/update-themes.sh` が `pkgs/hydenix-themes/*.nix`（`default.nix` と `utils/` 以下を除く）を 1 つずつ処理し、`rev` がブランチ名らしき形であれば `git ls-remote` で最新コミットハッシュに解決し、`nix-prefetch-url --unpack` で tar.gz を取得し直して `sha256` を再計算します。`rev` が変わっていなくても `sha256` だけ再検証するので、上流がタグや参照先を差し替えた場合にも追随できます。PR は `add-paths: "pkgs/hydenix-themes/*.nix"` で作成対象のファイルを絞り込んでおり、スクリプトが意図せず他のファイルを触っていてもそれが PR に混ざることはありません。PR が作られると条件なしに `gh pr merge --auto --rebase` で auto-merge を有効化します。`update-flake-lock.yml` と違って、このワークフロー自身は `nix flake check` のような検証を行わないまま auto-merge を有効化する点は覚えておく価値があります。

### dependabot.yml — GitHub Actions 自体の更新

これだけは独立したワークフローファイルではなく、GitHub がネイティブに提供する Dependabot の設定です。`package-ecosystem: github-actions` だけを対象にしており、`.github/workflows/*.yml` の中の `uses: owner/action@<sha>` を毎日 0 時 UTC に確認して新しいバージョンが出ていれば PR を作ります。コミット履歴に並ぶ `chore(deps): bump zizmorcore/zizmor-action from 0.6.0 to 0.6.1` のような PR がこれです。`cooldown.default-days: 7` によってリリースから 7 日は様子を見てから提案し、`open-pull-requests-limit: 10` で同時に開く PR 数の上限を設けています。renovate が Nix レベルの依存（flake input とパッケージのピン）を担当するのに対し、dependabot は Actions のバージョンだけを担当するという住み分けです。renovate や update-flake-lock、update-themes と異なり、Dependabot が作る PR を auto-merge するワークフローはこのリポジトリには見当たりません。作られた PR は他の PR と同じようにレビューとマージを待つことになります。

自動更新 PR を作る 3 つの仕組み（renovate・update-flake-lock・update-themes）のうち、renovate だけが `secrets.RENOVATE_TOKEN` という別途用意されたトークンを使い、残り 2 つは `secrets.GITHUB_TOKEN` を使っています。GitHub Actions には、ワークフローの実行が `GITHUB_TOKEN` を使って行った push や PR 作成は、他のワークフローの `push` / `pull_request` トリガーを起動しないという仕様があります。これを踏まえると、`update-flake-lock.yml` と `update-themes.yml` が作る PR には `flake-check.yml` や `typos.yml` などの通常の PR ゲートが自動では走らない可能性が高いということになります。`update-flake-lock.yml` がワークフロー内でわざわざ `nix flake check` を自前で 2 回実行してから結果を PR 本文に埋め込んでいるのは、この事情を踏まえると理解しやすい構成です。一方 `update-themes.yml` には同等の自前チェックが無く、そのまま auto-merge が有効化されます。Dependabot が作る PR はこの制約の対象外で、通常の `pull_request` トリガーを普通に起動します。

## ドキュメントの公開（pages.yml）

`docs/` を `mdbook build docs` でビルドするところまでは `push`・`pull_request`・`workflow_dispatch` のいずれでも実行され、ビルドが通るかどうかだけを確認します。実際に `peaceiris/actions-gh-pages` で公開する最後のステップには `if: ${{ github.ref == 'refs/heads/main' }}` という条件が付いており、`main` への push のときだけ動きます。公開先はワークフローを実行しているリポジトリ自身の `gh-pages` ブランチ・Pages サイトなので、このフォークの `main` に push しても florianvazelle 側の Pages は更新されません。[README.md](./README.md) の公式ドキュメントのリンクが指しているのは florianvazelle/hydenix 側の Pages で、このフォーク自身で GitHub Pages が有効化されているかどうかはリポジトリ設定次第です。

## すべてのワークフローに共通する設計

個々のワークフローを横断して、いくつか一貫した書き方があります。

`actions/checkout` や `cachix/install-nix-action` などの Action は、タグではなく完全な commit SHA で固定し、末尾に `# v7.0.1` のようにバージョン番号をコメントで添える形に統一されています。タグは指す先が後から変わり得ますが、SHA 固定であればワークフローが実際に実行する内容が変わらないことを保証できます。

`actions/checkout` の呼び出しはほぼ全てで `persist-credentials: false` を指定しています。これを指定しないと、チェックアウト後の作業ディレクトリに `GITHUB_TOKEN` を使った git の認証情報が残り、以降のステップで実行される任意のコマンドがそれを使って push できる状態になってしまいます。

権限は多くのワークフローでファイル冒頭の `permissions: {}` を起点にし、必要なジョブだけがその中で個別に権限を書き足す形です。例外もあり、`pages.yml` と `update-flake-lock.yml` はジョブが 1 つしかないためワークフロー冒頭で直接必要な権限を宣言しており、`update-themes.yml` にはワークフロー冒頭の `permissions` 自体が無くジョブ側だけで宣言しています。結果として実質的な権限の広さはどれも必要最小限に収まっていますが、書き方の統一という意味では完全に揃ってはいません。

シークレットは基本的に GitHub が自動発行する `GITHUB_TOKEN` で足りていますが、`renovate-local` ジョブだけは `RENOVATE_TOKEN` という別のトークンを使い、さらに `environment: renovate` による保護を経由します。

これらの約束事は `zizmor.yml` が継続的に検査している観点とおおむね一致しています。新しくワークフローを足すときや既存のものを書き換えるときは、この一覧を踏まえたうえで zizmor の結果も確認すると安全です。
